# GJ Mall Shop 后端面试讲解文档

这份文档不是单纯罗列技术栈，而是帮你把这个商城项目讲成“自己的项目”。面试时不要一上来背 Spring Boot、Redis、RabbitMQ，而是先讲业务流程，再讲每个技术点解决了什么问题。

你可以把这个项目理解成一句话：

> 这是一个前后端分离的多端商城项目，后端用 Spring Boot 做成单体多模块架构，覆盖了商品、购物车、下单、支付、库存、优惠券、秒杀、售后、后台权限和运营管理等完整商城流程。

---

## 1. 面试开场怎么介绍项目

### 1.1 简短版

如果面试官让你“介绍一下你的项目”，你可以先说：

> 我做的是一个完整的商城项目，包含 PC 商城、移动端、管理后台和后端服务。用户端可以浏览商品、搜索商品、加购物车、领优惠券、下单、支付、查看订单和申请售后；后台可以管理商品、库存、订单、发货、售后、支付记录、报表、角色权限和操作日志。
>
> 后端用的是 Spring Boot 2.7，整体是 Maven 多模块单体架构。核心数据存在 MySQL，购物车、登录状态、秒杀库存放 Redis，商品图文详情放 MongoDB，订单超时取消用 RabbitMQ 实现。

这个回答的重点是：

- 先说项目是干什么的。
- 再说你负责或熟悉的业务模块。
- 最后说技术栈。

不要一开始就说：

> 我用了 Spring Boot、MyBatis-Plus、Redis、RabbitMQ、MongoDB、JWT。

这样太像背技术栈，面试官会继续问：“那你用 Redis 解决了什么问题？”

---

### 1.2 稍微完整一点的版本

你可以这样说：

> 这个项目是一个电商商城系统，后端主要围绕商城核心交易链路来做，包括商品浏览、购物车、订单、支付、库存、营销和售后。
>
> 比如用户下单时，后端会校验商品是否上架、库存是否足够，然后锁定库存，生成订单和订单项，并发送一条 RabbitMQ 延迟消息。如果用户在规定时间内没有支付，消息到期后会触发订单超时取消，释放库存和优惠券。如果用户支付成功，支付模块会更新支付流水，再通知订单模块把订单改成待发货，同时把锁定库存转成销量。
>
> 所以这个项目我重点关注的不只是接口 CRUD，而是商城里比较容易出问题的地方，比如库存超卖、订单状态流转、支付重复回调、优惠券超发、秒杀高并发和后台权限控制。

这个版本更适合你想展示“我真的理解业务”的时候用。

## 2. 项目整体架构怎么讲

### 2.1 它是不是微服务？

不是。

这个项目应该说成：

> 单体多模块项目。

意思是：

- 部署的时候是一个后端应用。
- 代码上按业务拆成多个 Maven 模块。
- 模块之间通过 Java 依赖直接调用，不是远程调用。

### 2.2 为什么这样设计？

你可以这样回答：

> 因为商城业务比较多，如果所有代码都放在一个模块里，会越来越乱。所以我把公共能力、用户、商品、购物车、订单、支付、营销、后台管理拆成不同 Maven 模块。这样虽然部署还是一个服务，但是代码边界更清晰，后期如果要拆微服务，也比较容易按模块拆。

### 2.3 后端模块划分

后端主要在 `gj-mall-server` 下面：

| 模块 | 作用 | 面试说法 |
| --- | --- | --- |
| `gj-mall-common` | 统一返回、异常、错误码、常量 | 放所有模块都要用的公共类 |
| `gj-mall-framework` | JWT、拦截器、Web 配置、MyBatis-Plus 配置 | 放基础框架能力 |
| `gj-mall-user` | 用户、登录、地址、收藏、消息 | C 端用户相关 |
| `gj-mall-product` | 商品、分类、品牌、SKU、库存、搜索 | 商品中心 |
| `gj-mall-cart` | 购物车 | Redis 购物车 |
| `gj-mall-order` | 订单、订单项、物流、售后、评价 | 交易履约核心 |
| `gj-mall-pay` | 支付策略、支付流水、支付回调 | 支付中心 |
| `gj-mall-marketing` | 优惠券、秒杀活动 | 营销中心 |
| `gj-mall-admin-api` | 后台接口、权限、报表、日志 | 管理后台 |
| `gj-mall-app` | 启动模块 | 聚合所有业务模块启动 |

### 2.4 面试官可能问：为什么不用微服务？

你可以答：

> 这个项目目前更适合作为单体多模块。因为单体开发、调试、部署成本低，适合中小型商城或学习项目。项目内部已经按业务拆模块，保证代码边界清晰。等访问量上来之后，可以优先把商品、订单、支付、营销这些模块拆成独立服务。

这个回答比“我不会微服务”好很多。

## 3. 技术栈怎么讲

### 3.1 技术栈列表

| 技术 | 项目里怎么用 | 你应该怎么说 |
| --- | --- | --- |
| Spring Boot | 后端主框架 | 用来快速开发 REST API |
| MyBatis-Plus | 操作 MySQL | 做 CRUD、分页、逻辑删除、自动填充 |
| MySQL | 核心业务数据 | 存用户、商品、订单、支付流水、优惠券 |
| Redis | 高频数据和临时状态 | 存购物车、token、秒杀库存 |
| Redisson | 分布式锁 | 防止优惠券并发领取超发 |
| RabbitMQ | 异步消息 | 做订单超时取消 |
| MongoDB | 文档型数据 | 存商品富文本详情和图片说明 |
| JWT | 登录鉴权 | 用户和后台管理员登录凭证 |
| AOP | 权限和操作日志 | 后台权限校验、记录操作日志 |
| Knife4j | 接口文档 | 查看和调试后端接口 |

### 3.2 更自然的说法

面试官问“你项目用了哪些技术？”你可以这样答：

> 后端主要是 Spring Boot + MyBatis-Plus + MySQL。MySQL 存核心交易数据，比如商品、订单、支付流水、优惠券这些。
>
> Redis 主要用在三个地方：第一个是购物车，因为购物车读写频繁；第二个是登录 token 白名单，用来支持登出和 token 失效；第三个是秒杀库存，因为秒杀不能直接打数据库。
>
> RabbitMQ 用在订单超时取消，下单后发送延迟消息，超时后检查订单是否未支付。
>
> MongoDB 用在商品详情，因为商品详情有 HTML、图片数组、售后说明，这种内容结构比较灵活，不太适合全放 MySQL 字段里。

## 4. 登录鉴权功能

### 4.1 项目里怎么做登录？

项目里有两类登录：

- 普通用户登录。
- 后台管理员登录。

登录成功后，后端会生成两个 token：

- `accessToken`：短期访问接口用。
- `refreshToken`：accessToken 过期后刷新用。

JWT 里面会放：

- `uid`：用户 ID。
- `typ`：用户类型，普通用户是 `user`，后台管理员是 `admin`。

### 4.2 为什么 JWT 还要配合 Redis？

只用 JWT 有一个问题：

> JWT 一旦发出去，在过期之前默认都是有效的。

比如用户点了退出登录，如果后端不保存状态，那么旧 token 其实还能继续访问接口。

这个项目的做法是：

- 登录成功后，把当前有效的 accessToken 存到 Redis。
- 每次请求接口时，先解析 JWT。
- 再去 Redis 判断这个 token 是不是当前有效 token。
- 如果 Redis 里没有，说明已经退出登录或者 token 已失效。

### 4.3 你可以这样说

> 我项目里没有只依赖 JWT 自身过期时间，而是 JWT + Redis 一起用。JWT 负责无状态解析用户身份，Redis 负责保存当前有效 token。这样用户退出登录时，只要删除 Redis 里的 token，就能让旧 token 立刻失效。

### 4.4 面试官可能追问：Redis 存 token 有什么好处？

答：

> 好处是可以主动控制 token 是否有效，比如用户退出、后台禁用用户、强制下线，都可以删除 Redis 中的 token。否则单纯 JWT 在过期前很难主动失效。

### 4.5 面试官可能追问：怎么区分普通用户和后台用户？

答：

> JWT 里有一个 `typ` 字段，普通用户是 `user`，后台用户是 `admin`。拦截器解析 token 后会把用户 ID 和用户类型放到 `UserContext`，后续 service 就可以直接拿当前用户信息。

## 5. 购物车功能

### 5.1 购物车为什么用 Redis？

购物车有几个特点：

- 读写频繁。
- 数据临时性比较强。
- 对强事务要求没有订单那么高。
- 用户每次加购、改数量、勾选商品都要快速响应。

所以项目里购物车放 Redis。

### 5.2 Redis 里存什么？

Redis 里不是存完整商品信息，而是存最小信息：

- `skuId`
- 数量 `quantity`
- 是否选中 `selected`
- 加入时间 `addTime`

展示购物车时，再去 MySQL 查最新商品信息：

- 商品名
- 图片
- 价格
- 库存
- 是否上架

### 5.3 为什么不把价格也存在 Redis？

可以存，但不能完全相信 Redis 里的旧价格。

比如用户昨天加入购物车时价格是 999，今天商家改成 899。如果购物车一直显示旧价格，就不准确。

所以项目里展示购物车时，会重新查商品表，用当前价格重新计算金额。

### 5.4 你可以这样说

> 购物车我用 Redis Hash 存，每个用户一个购物车 key，每个 SKU 是 hash 里的一个 field。Redis 里只存 skuId、数量、选中状态这些轻量数据。查询购物车时再批量查 MySQL，补充商品实时价格、库存和上下架状态。这样既保证访问快，也避免展示旧商品数据。

### 5.5 面试官可能问：购物车商品下架了怎么办？

答：

> 查询购物车时会查商品当前状态。如果商品不存在、下架或者库存不足，会把购物车项标记成无效，并告诉前端原因，比如商品已下架、库存不足。这样用户不能用无效商品下单。

## 6. 商品模块

### 6.1 商品 SPU 和 SKU 怎么理解？

你可以用很简单的话讲：

> SPU 是一个商品，比如 iPhone 16。SKU 是具体规格，比如 iPhone 16 黑色 256G。

项目里：

- `pms_spu` 存商品主信息。
- `pms_sku` 存具体规格、价格、库存。

### 6.2 商品详情为什么用 MongoDB？

MySQL 适合结构稳定的数据，比如：

- 商品 ID
- 商品名
- 分类
- 品牌
- 价格
- 状态

但是商品详情页内容比较灵活，比如：

- 富文本 HTML
- 多张详情图
- 包装清单
- 售后说明

这些内容字段长、结构不固定，所以项目用 MongoDB 存。

### 6.3 你可以这样说

> 商品基础信息我放 MySQL，因为这些字段结构固定，而且经常参与查询、排序和筛选。商品详情图文放 MongoDB，因为详情内容比较长，结构也可能变化，放文档数据库更灵活。

### 6.4 商品搜索怎么做？

项目当前不是 Elasticsearch，而是基于 MySQL 做搜索。

支持：

- 商品名称搜索。
- 副标题搜索。
- SKU 名称搜索。
- SKU 编码搜索。
- 分类匹配。
- 品牌匹配。
- 一些常见品牌别名和关键词处理。

### 6.5 面试官问为什么不用 Elasticsearch？

可以答：

> 目前项目数据量不大，所以先用 MySQL 做关键词搜索、分类筛选、品牌筛选和排序，能满足基本商城搜索。后续如果商品量变大，或者需要分词、相关性排序、拼音搜索，就可以把商品数据同步到 Elasticsearch。

这个回答很稳，因为你承认当前实现，也说明后续优化方向。

## 7. 库存设计

### 7.1 库存字段怎么理解？

SKU 里有几个关键字段：

- `stock`：可售库存。
- `locked_stock`：已下单但未支付的锁定库存。
- `sale_count`：销量。

### 7.2 为什么要有锁定库存？

因为用户下单后还没有付款。

如果下单时不扣库存，很多人同时下单，后面支付时可能库存不够。

如果下单时直接算卖出，用户不付款又会导致库存不准确。

所以项目采用：

1. 下单时扣可售库存，增加锁定库存。
2. 支付成功时减少锁定库存，增加销量。
3. 取消或超时时释放锁定库存，回到可售库存。

### 7.3 你可以这样说

> 我把库存分成可售库存和锁定库存。用户下单成功后，只是锁库存，不代表真正卖出。支付成功后才把锁定库存转成销量。如果订单取消或者超时未支付，就把锁定库存释放回可售库存。

### 7.4 下单怎么防止超卖？

关键是不要这样做：

1. 先查库存。
2. 在 Java 里判断库存够不够。
3. 再更新库存。

并发时两个请求可能同时查到库存够，然后都扣成功，导致超卖。

项目里用数据库原子更新：

```sql
UPDATE pms_sku
SET stock = stock - #{quantity},
    locked_stock = locked_stock + #{quantity}
WHERE id = #{skuId}
  AND stock >= #{quantity}
```

如果影响行数大于 0，说明扣库存成功。

如果影响行数等于 0，说明库存不足。

### 7.5 面试官可能问：为什么不用 synchronized？

答：

> synchronized 只能锁当前 JVM，如果项目多实例部署，就锁不住其他实例。而数据库条件更新是落在数据库层的，多个应用实例同时访问也能保证库存不会扣成负数。

## 8. 下单流程

### 8.1 普通下单流程

你可以按这个顺序记：

1. 判断是购物车下单还是直接购买。
2. 获取选中的商品。
3. 校验商品是否存在、是否上架、库存是否足够。
4. 获取收货地址，保存地址快照。
5. 锁定 SKU 库存。
6. 计算商品总金额。
7. 计算运费。
8. 校验优惠券并计算优惠金额。
9. 生成订单。
10. 生成订单项。
11. 如果是购物车下单，移除已下单购物车项。
12. 发送 RabbitMQ 延迟消息，用于超时取消。

### 8.2 为什么订单里要存地址快照？

因为用户下单后，可能修改自己的收货地址。

订单应该保存下单时的地址，而不是每次都查用户当前地址。

否则用户修改地址后，历史订单地址也变了。

### 8.3 你可以这样说

> 下单时我会把收货人、手机号、地址这些信息保存成订单快照。因为订单是历史交易记录，不能因为用户后面修改地址而影响已经生成的订单。

### 8.4 为什么订单项也要存商品名和价格？

同理。

商品后续可能改名、改价、换图片。

订单项必须保存下单时的商品名、SKU 名、价格、图片、规格。

### 8.5 你可以这样说

> 订单项里我会保存商品快照，比如商品名、规格、价格、图片。这样商品后面改价或者下架，也不会影响历史订单展示。

## 9. 订单状态流转

### 9.1 常见订单状态

项目里的订单状态大概可以这样理解：

| 状态 | 含义 |
| --- | --- |
| 待付款 | 用户已下单，还没支付 |
| 待发货 | 用户已支付，商家还没发货 |
| 待收货 | 商家已发货，用户还没确认收货 |
| 已完成 | 用户确认收货 |
| 已取消 | 用户取消或超时取消 |
| 退款中 | 售后处理中 |
| 已退款 | 退款完成 |

### 9.2 面试讲法

> 订单状态不能随便改，必须按业务流程流转。比如待付款可以取消，也可以支付；支付后变成待发货；后台发货后变成待收货；用户确认收货后变成已完成。售后申请时会进入退款中，退款完成后变成已退款。

### 9.3 面试官可能问：如果用户支付时订单已经取消怎么办？

答：

> 支付前和支付回调处理时都会检查订单状态。如果订单已经取消，就不能再改成已支付。支付成功处理里也做了幂等判断，只有待付款状态才能改成待发货。

## 10. 订单超时取消

### 10.1 为什么需要订单超时取消？

用户下单后会锁库存。

如果用户一直不支付，库存就一直被占用。

所以需要超时取消订单，释放库存。

### 10.2 这个项目怎么做？

项目用 RabbitMQ 的 TTL + 死信队列实现。

流程：

1. 用户下单成功。
2. 后端发送订单 ID 到延迟队列。
3. 延迟队列设置 TTL，比如 30 分钟。
4. 消息过期后进入死信交换机。
5. 死信交换机把消息路由到超时队列。
6. 消费者收到订单 ID。
7. 查询订单状态。
8. 如果还是待付款，就取消订单，释放库存和优惠券。
9. 如果已经支付或取消，就忽略。

### 10.3 你可以这样说

> 我没有用定时任务扫订单表，而是每个订单创建后发送一条延迟消息。时间到了只检查这一单，如果还是待支付就取消。这样比定时扫表更精准，也减少数据库压力。

### 10.4 面试官可能问：为什么消费者还要查订单状态？

答：

> 因为消息到期时，订单可能已经支付了。如果不查状态直接取消，就会把已支付订单取消掉。所以消费者必须二次确认订单仍然是待付款。

### 10.5 面试官可能问：消息消费失败怎么办？

当前项目里处理失败会记录日志并 ack，避免阻塞队列。

你可以说：

> 当前项目是学习和演示场景，消费者异常时会记录日志并确认消息，避免队列阻塞。如果是生产环境，我会考虑失败重试、死信队列记录、告警和补偿任务，比如定时扫描长时间待支付订单做兜底。

这个回答比较成熟。

## 11. 支付模块

### 11.1 支付为什么要单独一个模块？

支付是订单系统里风险比较高的部分。

它涉及：

- 支付流水。
- 支付渠道。
- 回调通知。
- 金额校验。
- 重复回调。
- 退款。

所以项目里单独拆了 `gj-mall-pay`。

### 11.2 支付策略模式怎么理解？

项目里定义了一个 `PayStrategy` 接口。

不同支付方式实现这个接口：

- Mock 支付。
- 微信支付。
- 支付宝支付。

发起支付时，根据前端传的渠道选择对应策略。

### 11.3 你可以这样说

> 支付这块我用了策略模式，把不同支付渠道的差异封装到不同策略类里。业务层只依赖统一的支付接口。后续如果要接入新的支付方式，只要新增一个策略实现，不需要大改原来的支付流程。

### 11.4 支付流程

1. 用户选择订单发起支付。
2. 后端校验订单是否属于当前用户。
3. 校验订单是否待付款。
4. 生成支付流水。
5. 根据支付渠道选择策略。
6. 调用支付策略。
7. Mock 支付会立即返回成功。
8. 支付成功后更新支付流水。
9. 通知订单模块修改订单状态。

### 11.5 支付流水有什么用？

支付流水是为了记录每一次支付请求。

包括：

- 支付单号。
- 订单号。
- 用户 ID。
- 支付渠道。
- 支付金额。
- 支付状态。
- 第三方支付单号。
- 回调数据。

### 11.6 你可以这样说

> 订单表只记录订单当前状态，支付流水表记录每次支付请求和支付结果。这样后续排查问题时，可以看订单对应的支付流水、渠道回调和第三方支付单号。

## 12. 支付回调

### 12.1 支付回调为什么重要？

真实支付里，用户支付成功后，支付平台会通知我们的后端。

后端不能简单地“收到回调就改订单成功”。

因为可能有这些问题：

- 回调是伪造的。
- 金额被篡改。
- 支付渠道不一致。
- 同一条回调重复发送。
- 回调顺序异常。

### 12.2 项目里做了哪些校验？

支付回调主要做：

1. 渠道校验。
2. 签名校验。
3. 支付流水查询。
4. 金额校验。
5. 支付状态幂等判断。
6. 更新支付流水。
7. 更新订单状态。
8. 保存回调记录。

### 12.3 什么是幂等？

用简单话说：

> 同一个请求执行一次和执行多次，结果应该一样。

支付回调可能重复来。

如果第一次已经把订单改成已支付，第二次再来时就不能重复扣库存、重复改状态、重复发消息。

项目处理方式：

- 查询支付流水状态。
- 如果已经成功，就认为是重复回调，直接忽略。
- 只记录回调，不重复处理业务。

### 12.4 你可以这样说

> 支付回调我重点处理了幂等问题。因为第三方支付平台可能重复通知，所以我会先查支付流水状态。如果支付流水已经成功，就直接返回，不再重复更新订单。只有待支付状态的流水，才会继续做金额校验和订单状态更新。

### 12.5 金额校验怎么讲？

> 回调里的金额必须和支付流水金额一致。如果订单金额是 100，回调金额是 1，说明数据有问题，不能更新订单为已支付。

### 12.6 签名校验怎么讲？

> 回调会带签名，后端用约定好的密钥按固定规则重新计算签名，然后和请求里的签名比较。如果不一致，就说明回调可能被篡改或伪造。

## 13. 退款和售后

### 13.1 售后流程

用户可以对订单申请售后。

常见类型：

- 仅退款。
- 退货退款。

流程大概是：

1. 用户提交售后申请。
2. 后端校验订单是否属于当前用户。
3. 校验订单状态是否允许售后。
4. 校验是否在售后时间范围内。
5. 创建售后单。
6. 订单进入退款中。
7. 后台审核。
8. 如果是退货退款，用户填写退货物流。
9. 后台确认收货。
10. 后台退款。
11. 订单变为已退款。

### 13.2 为什么要保存订单状态快照？

用户申请售后后，订单会变成退款中。

如果用户取消售后，需要恢复到原来的订单状态。

所以售后单里保存了申请时的订单状态快照。

### 13.3 你可以这样说

> 用户申请售后时，我会把当前订单状态保存到售后单里。这样如果售后取消，可以把订单恢复到申请前的状态，避免订单状态丢失。

### 13.4 售后资格怎么判断？

售后不是任何订单都能申请。

通常要判断：

- 订单是否已支付。
- 订单是否已取消。
- 是否已经退款。
- 是否超过售后期限。
- 当前是否已有处理中的售后单。

### 13.5 你可以这样说

> 售后申请前，我会先做资格校验，比如订单是否属于当前用户，是否已支付，是否已退款，是否超过售后期限，以及是否已经有处理中的售后单。这样可以避免重复申请或非法申请。

## 14. 优惠券功能

### 14.1 优惠券有哪些点？

优惠券主要有：

- 后台创建优惠券。
- 用户领券。
- 我的优惠券。
- 下单可用券列表。
- 结算页最优券。
- 使用优惠券。
- 订单取消释放优惠券。

### 14.2 领券怎么防止超发？

如果一张券只有 100 张，同时 1000 个人抢，不能发出去 101 张。

项目里用了两层保护：

第一层：Redisson 分布式锁。

> 同一张券同一时间只有一个线程能处理领取。

第二层：数据库条件更新。

```sql
UPDATE sms_coupon
SET received_count = received_count + 1
WHERE id = ?
  AND received_count < total_count
```

如果影响行数是 0，说明已经领完。

### 14.3 你可以这样说

> 领券这里我用了 Redisson 分布式锁控制同一张券的并发领取，同时数据库更新也加了 received_count < total_count 条件。这样即使并发很高，也不会超过总发放数量。

### 14.4 下单用券怎么校验？

下单时会校验：

- 这张券是不是当前用户的。
- 是否未使用。
- 是否启用。
- 是否在有效期内。
- 订单金额是否满足门槛。

### 14.5 订单取消后优惠券怎么办？

如果订单取消，优惠券要释放。

也就是：

- 用户券状态从已使用改回未使用。
- 优惠券 used_count 减少。

### 14.6 面试官可能问：为什么领券用了锁，下单用券没有用锁？

可以答：

> 领券的并发竞争集中在同一张券的总库存，所以用了分布式锁防止超发。下单用券时主要是校验用户自己的券状态，支付成功后才核销。如果生产环境要更严谨，可以对用户券也做状态条件更新，比如只有 status=0 才能改成 status=1，避免重复核销。

## 15. 秒杀功能

### 15.1 秒杀和普通下单有什么不同？

普通下单可以直接用 MySQL 原子扣库存。

但秒杀瞬间并发高，如果所有请求都打 MySQL，数据库压力很大。

所以秒杀库存放 Redis。

### 15.2 秒杀流程

1. 后台创建秒杀活动。
2. 后台上架活动。
3. 秒杀 SKU 库存预热到 Redis。
4. 用户发起秒杀请求。
5. Redis Lua 脚本判断限购和库存。
6. Redis 扣库存成功。
7. 创建秒杀订单。
8. 如果创建订单失败，回滚 Redis 库存。
9. 支付成功后更新订单和库存销量。

### 15.3 为什么用 Lua？

因为秒杀时需要把多个操作变成原子操作：

- 查用户是否超过限购。
- 查库存是否足够。
- 扣减库存。
- 记录用户已购买数量。

如果分成多条 Redis 命令，并发时可能出问题。

Lua 脚本在 Redis 中一次执行，中间不会被其他请求打断。

### 15.4 你可以这样说

> 秒杀我用 Redis Lua 做原子扣减。Lua 脚本里同时判断用户限购、判断库存、扣减库存和记录购买标记。这样可以避免多个 Redis 操作之间被并发请求插入，防止超卖和超过限购。

### 15.5 面试官可能问：Redis 扣成功但订单创建失败怎么办？

答：

> 创建订单外面有 try-catch。如果订单创建失败，会调用释放库存逻辑，把 Redis 库存加回去，同时减少用户购买标记，避免用户明明没下单成功却占用了秒杀资格。

### 15.6 面试官可能问：Redis 秒杀库存和数据库库存怎么保持一致？

答：

> 秒杀请求先扣 Redis，创建订单时还会通过数据库库存锁定做一次校验和扣减。Redis 主要承接高并发入口，数据库作为最终落库。生产环境还可以增加异步对账或补偿任务，定期校验 Redis 活动库存、订单数量和数据库库存。

## 21. 常见面试题和回答

### 21.1 你这个项目最大的难点是什么？

可以答：

> 我觉得最大的难点是订单链路的一致性。因为下单会影响库存、优惠券、订单、购物车，支付成功又会影响支付流水、订单状态、库存销量和用户消息。如果中间某一步处理不好，就会出现超卖、重复支付、库存不释放、优惠券状态错误等问题。
>
> 所以我在下单时做了库存锁定，支付成功才消费库存，订单取消或超时会释放库存和优惠券。支付回调也做了幂等和金额校验，避免重复回调导致状态异常。

### 21.2 Redis 在项目里用在哪些地方？

答：

> 主要用在三个地方。第一是购物车，用 Redis Hash 存用户购物车，读写比较快。第二是登录 token 白名单，JWT 解析身份，Redis 判断 token 是否仍然有效。第三是秒杀库存，把秒杀库存预热到 Redis，通过 Lua 脚本原子扣减，减轻数据库压力。

### 21.3 RabbitMQ 用来做什么？

答：

> RabbitMQ 主要用来做订单超时取消。下单成功后发送延迟消息，消息过期后进入死信队列，消费者检查订单是否还待支付。如果还没支付，就取消订单并释放库存和优惠券。

### 21.4 为什么不用定时任务取消订单？

答：

> 定时任务也可以做，但是要不断扫描订单表。订单量大时会有压力，而且取消时间不够精准。延迟消息是每个订单一条消息，到时间只检查这一单，更精准。生产环境也可以加定时任务做兜底补偿。

### 21.5 怎么防止库存超卖？

答：

> 普通下单用数据库条件更新，更新条件里带 `stock >= quantity`，只有库存足够时才能扣减成功。秒杀场景先用 Redis Lua 原子扣减库存，再创建订单，避免高并发直接打数据库。

### 21.6 支付回调重复来了怎么办？

答：

> 我会先查支付流水状态。如果流水已经是支付成功，就认为是重复回调，直接返回，不会重复修改订单状态，也不会重复扣库存。

### 21.7 为什么要支付流水表？

答：

> 订单表只表示订单当前状态，支付流水表记录每一次支付请求和支付结果，包括支付单号、渠道、金额、第三方单号和回调数据。这样方便对账和排查支付问题。

### 21.8 优惠券怎么防止超发？

答：

> 领券时用 Redisson 对优惠券 ID 加分布式锁，同时数据库更新时加 `received_count < total_count` 条件。这样应用层和数据库层都有保护。

### 21.9 秒杀为什么用 Lua？

答：

> 因为秒杀要同时判断限购、判断库存、扣库存和记录用户购买标记。如果拆成多条 Redis 命令，并发时中间可能被其他请求插入。Lua 脚本在 Redis 中原子执行，可以保证这些操作不会被打断。

### 21.10 商品详情为什么用 MongoDB？

答：

> 商品基础信息结构稳定，适合放 MySQL。商品详情页有 HTML、图片数组、包装清单、售后说明，内容比较长，结构也可能变化，所以用 MongoDB 存文档更灵活。

### 21.11 后台权限怎么实现？

答：

> 后台用 RBAC 模型，管理员绑定角色，角色绑定权限。接口访问时用 AOP 根据请求路径匹配需要的权限编码，再判断当前管理员是否拥有权限。

### 21.12 操作日志为什么用 AOP？

答：

> 因为操作日志是横切逻辑，很多后台接口都需要记录。如果每个接口手写日志，会重复又容易漏。用 AOP 可以统一拦截后台的新增、修改、删除操作，记录操作人、请求参数、耗时和结果。

## 22. 你可以主动讲的项目亮点

面试时不要等面试官问完所有问题，你可以主动说：

> 这个项目里我觉得比较有代表性的点有三个。
>
> 第一个是订单库存一致性。下单先锁库存，支付成功才消费库存，取消和超时会释放库存。
>
> 第二个是支付回调处理。支付回调做了签名校验、金额校验、渠道校验和幂等处理，避免重复回调或异常回调影响订单。
>
> 第三个是高并发场景。购物车用 Redis，秒杀库存用 Redis Lua，优惠券领取用 Redisson 锁加数据库条件更新，都是围绕商城高频场景做的。

## 23. 不要说错的地方

### 23.1 不要说这是微服务

应该说：

> 单体多模块。

### 23.2 不要说已经接入真实微信支付和支付宝支付

应该说：

> 当前主要实现了 Mock 支付，微信和支付宝是按策略模式预留扩展点。

### 23.3 不要说用了 Elasticsearch

应该说：

> 当前搜索基于 MySQL 做关键词、品牌、分类和 SKU 维度匹配。后续数据量大可以接 Elasticsearch。

### 23.4 不要说 Redis 保证了最终数据一定正确

应该说：

> Redis 承担高频访问和秒杀入口，最终交易数据仍然以 MySQL 落库为准。

## 24. 最终背诵版

这段你可以多读几遍，面试时按自己的话说：

> 我这个项目是一个完整商城系统，后端用 Spring Boot 做成单体多模块架构。模块上拆成用户、商品、购物车、订单、支付、营销、后台管理这些部分。
>
> 用户端的核心流程是：浏览商品，加购物车，选择优惠券，下单，支付，后台发货，用户确认收货，后续可以申请售后。后台主要负责商品、库存、订单、物流、售后、支付记录、报表和权限管理。
>
> 我重点理解的是订单链路。用户下单时，后端会先校验商品和库存，然后锁定库存，生成订单和订单项，同时发送 RabbitMQ 延迟消息。如果用户超时未支付，消息到期后会取消订单并释放库存和优惠券。如果用户支付成功，支付模块会更新支付流水，并通知订单模块把订单改成待发货，同时把锁定库存转成销量。
>
> 项目里 Redis 主要用在购物车、token 白名单和秒杀库存。购物车用 Redis Hash 存最小数据，展示时再查 MySQL 补实时商品信息。秒杀库存预热到 Redis，通过 Lua 脚本原子判断限购和扣库存。优惠券领取用了 Redisson 锁和数据库条件更新防止超发。
>
> 支付模块用了策略模式，方便扩展不同支付渠道。支付回调做了签名校验、金额校验、渠道校验和幂等处理，避免重复回调导致订单状态异常。
>
> 所以这个项目不是简单 CRUD，我主要关注的是商城里容易出问题的几个点：库存不能超卖，订单状态不能乱跳，支付不能重复处理，优惠券不能超发，后台操作要有权限和日志。

## 25. 建议你面试前重点准备

最重要的 8 个问题：

1. 介绍项目整体业务流程。
2. 为什么做成单体多模块？
3. JWT + Redis 登录鉴权怎么做？
4. 购物车为什么放 Redis？
5. 下单怎么防止库存超卖？
6. 订单超时取消怎么实现？
7. 支付回调怎么保证幂等？
8. 秒杀为什么用 Redis Lua？

如果这 8 个问题你能用自己的话说清楚，这个项目就已经能支撑一轮比较完整的后端面试。
